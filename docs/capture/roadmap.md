# OpenStage Capture: Build Roadmap

**Status:** Draft v0.1
**Built from:** the [product brief](product-brief.md), the [requirements document](prd.md) (46+ stories), and [what Capture needs from OpenStage](openstage-requests.md)
**Scope:** Release 1, Windows 11 and later
**Imported from:** `jasonswrench-beep/claude-test`, branch `claude/screen-recording-software-brief-ivhxqp`, commit `9c2c6fa303709f73650361e31e0a2cf12c5a5ce3` (2026-10-15). Apart from this line, the roadmap below is copied word for word.

> **How to read this.** The roadmap gives an *order*, not dates, because nobody can honestly date work that depends on testing on a real Windows machine and on changes inside OpenStage. Each phase says what gets built, which requirement stories it covers, where it can be tested, and what has to be true before the next phase starts (the *exit check*). Story numbers (A1, C3, and so on) refer to the requirements document.

## 1. Ground rules

1. **Walking skeleton first.** The first thing built is a thin, working path from "start recording" to "recover a crashed recording," with a fake (synthetic) source of sound and picture. Real capture is then added to a skeleton that already works and is already tested.
2. **Accessibility is built in every phase,** not saved for the end. Every phase's exit check includes the keyboard and screen reader checks for what it built.
3. **Test where it can be tested.** Pure logic (protocol, project format, crash recovery, edit model) is built and tested in the cloud build environment. Anything that touches Windows (screen capture, sound devices, encoders, hotkeys, screen readers) is written there but **tested on the owner's Windows machine** with double-click scripts, and results are recorded.
4. **Nothing is claimed that was not tested** (R9 in the requirements document).
5. **Checkpoints, not promises.** At marked points the owner can change course. The two main ones: if OpenStage's prerequisites prove large, revisit what Release 1 includes; if speech recognition fails its audit, it leaves Release 1.
6. **License and rules checks run on every change** from the first line of code (G4).

| Who | Does |

## 3. Where the code lives

- **Now:** in this repository under `capture/`, as a Cargo workspace (Rust) with these crates: `openstage-capture-protocol`, `openstage-capture-project`, `openstage-capture` (the engine), and `openstage-capture-cli` (the `openstage-capture` program).
- **Later:** when the owner agrees, the `capture/` folder moves into the OpenStage repository, and the editor panels (TypeScript) are added to `editor/src/`.

**Storage decision (2026-10-13, decided after a crash test on the owner's computer; the owner can veto).** A real recording is one fragmented MP4 per take, written by Windows' own video tools, plus our own append-only interaction log. See Phase 2, slice 2.2b. This replaces the earlier plan of storing video in our own checksummed segment records (which remain for the test source).

**Architecture decision (made on the owner's delegation; the owner can veto).** *Edit operations* (trim, split, join, reorder, undo) live in **TypeScript** in the editor, like the existing Timeline model, and are saved as an edit decision list in the capture project. The Rust side **reads and validates** that list and **renders** it. This avoids sending every keystroke of an edit across a process boundary and matches OpenStage's rule that editor logic is TypeScript.

What follows was the design as built and tested here. `record --source screen` now records sound with the picture. Each take holds `screen.mp4` with the microphone and the computer's sound mixed into one AAC sound track (what every player plays), plus `mic.wav` and `system.wav` with each sound alone (what the editor needs; the echo the owner heard is exactly the case). The sound is laid on the recording clock, so it is as long as the picture; sound heard during a pause or while the recorder was starting up is thrown away; the separate files stay playable after a crash because their length is written into the header every second after the sound is on disk, and `recover` repairs them. New options `--microphone` and `--output` (a number, part of a name, `default`, or `none`) choose the devices before the countdown, and the chosen devices are said in words (`sound-devices`), so a wrong choice is explained before anything is recorded. After the recording the program reads everything back: the video, the video's sound track, and each sound file (`video-readback`, `audio-readback`, `microphone-file`, `system-sound-file`), and warns in plain words if a track is silent (`track-silent`, with advice that fits a microphone or the computer's sound). Sound levels (`mic`, `system`) are reported while recording. The project format is now 0.2.1. **Two decisions made on the owner's delegation, either can be vetoed:** (1) the separate tracks are WAV files beside the MP4, not extra sound tracks inside it, because as far as is known Windows' own MP4 writer is built for one picture and one sound stream (this was not confirmed; it would not change what the editor gets); (2) if a sound device stops in the middle of a recording (a microphone unplugged, a headset switched), the take ends with a plain message and everything recorded until then is kept, rather than carrying on silently without that sound, because a lesson with a missing voice should not look finished; carrying on with a warning needs a way for the recorder to warn during a recording, which does not exist yet. 213 automated tests pass here (215 on Windows). The Windows parts (the AAC encoder, the sound track in the fragmented MP4, reading the sound track back) are type-checked here and, by the owner's report, worked when run. **Echo check, built after the owner's report (not yet run on Windows):** after a recording with both sounds, and in `audio-test`, the program compares how loud the microphone is with how loud the computer's sound is, moment by moment (20 millisecond windows, delays up to 300 milliseconds). If they rise and fall together and the microphone carries at least about 3 percent of the computer's sound, it says an echo is likely, how much quieter and how much later, and suggests headphones; the separate files let the editor fix it afterwards. It says plainly when there was too little computer sound to tell. **The thresholds are first estimates tested only on made-up sound** (they catch a clear echo, ignore an unrelated voice, and ignore a leak 46 decibels down); they can miss an echo that is quiet next to a loud voice. Real recordings, with and without headphones, are needed to tune them. 223 automated tests pass here (225 on Windows). **Balance, built after the owner's second report (not yet run on Windows).** The owner found the microphone and the computer's sound at very different loudness and asked whether they can be on separate tracks so they can be balanced. They already are separate: `mic.wav` and `system.wav` in each take hold each sound exactly as heard, and the editor will balance them. What was heard in the video was the fixed one-to-one mix. Separate sound tracks *inside* the MP4 are not possible with Windows' own MP4 writer, which takes one picture stream and one sound stream ([MPEG-4 file sink](https://learn.microsoft.com/en-ie/Windows/Win32/medfound/mpeg-4-file-sink); the sink writer documentation does not say it lifts that limit, so this is an inference and was not tried). New: `--mic-gain-db` and `--system-gain-db` (whole decibels, -40 to 20) adjust only the mix inside the video, are written into `take.json` (`mix` on the video, format 0.2.2), and never touch the separate files; and after a recording, and in `audio-test`, a `balance` check measures how loud each sound is while it is making sound, says in words how far apart they are, and, when the computer's sound is as loud as the voice or louder, gives a number to try (it aims for the voice about 6 decibels above the computer's sound). The owner's fresh `audio-test` run (Shure MV7, output 9) showed the voice peaking at 0.12 and the computer's sound at 0.57, a clock difference of 11 ms, and an echo check that said the microphone does not seem to be hearing the computer's sound (0.32 out of 1); whether speakers or headphones were used in that run was not stated, so the echo check has not yet been seen to catch a real echo. 238 automated tests pass here (240 on Windows). **Slice 2.5, long recordings you can trust: built, not yet run on Windows** (the owner chose to work on it next). Four pieces, all added to the real recorder and its tests. (1) *Timing test* (`timing-test`, `TEST SYNC TIMING.bat`): every picture and every packet of sound now carries the moment Windows captured it and the moment it reached the program, on the computer's high resolution clock, and the test reports how late each arrives and how far out of step sound and picture would be if placed by arrival (the passing limit is 40 ms). It also checks that Windows' picture times and sound times really are on the same clock as the program's: if they are not, it says so. This is the measurement the earlier flash-and-beep idea could not give, because it does not depend on when a test program happens to flash and beep. (2) *Numbers for long runs*: the recorder counts skipped steps of the 30-picture rhythm, pictures Windows threw away, processor use, memory use (looked at every 10 seconds), and for each sound how far the sound card ran from the computer's clock and the worst a sound played earlier or later than its picture; after the recording it says them in words (`run-summary`, `run-cpu`, `run-memory`, `run-sound-microphone`, `run-sound-system`), and once a minute it writes a memory and processor line to standard error. `--strict` makes them count toward pass or fail. `TEST LONG RECORDING.bat` asks for a length (10 minutes by default; 60 for the checkpoint CP-2), pauses 20 seconds in the middle, and prints the result. (3) *Crash test of the real recorder* (`recorder-crash-test`, `TEST RECORDER CRASH.bat`): records with sound through a pause, kills the recorder without warning, repairs the project, and checks the video, the sound track inside it, and each sound file, and how much was lost (within 3 seconds passes; the product allows 10). (4) *Start-up delay*: the screen capture, the sound, and the video encoder (woken with a throwaway file) are now started when the countdown starts, so recording begins when the countdown ends instead of about 1.3 seconds later; the log prints the timing of each step so the saving can be read off. Problems with the screen or a sound device are now reported at the start of the countdown. **Not yet known:** the actual numbers on the owner's computer for all four; whether Windows' sound packet times and picture times agree with each other (the timing test will say); whether warming the encoder helps. **Known gap:** the checkpoint wants sound within 40 ms of the picture, and the sound-alignment code as built can hold sound 40 to 80 ms behind when a sound card's clock runs fast; the long test will show whether that matters on this computer, and placing sound and picture by their capture times (which the stamps now make possible) is the planned fix if it does. 271 automated tests pass here (273 on Windows). **Slice 2.5 results, from the owner's first run of all four scripts on the same day.** *Timing test: passed.* Pictures reach the program 11 ms *before* the time Windows stamps on them (Windows appears to stamp a picture with about the moment it will be shown), the microphone's sound 6 ms after its stamp (0 to 12), the computer's sound 11 ms after (6 to 17). Two real bugs were found in Phase 1 and fixed, each with a regression test that fails without the fix:

1. A time subtraction could overflow when handling a command took longer than the recorder's own step (found by the integration tests in the cloud).
