The base (the recording engine and the editing parts, copied from OpenStage Author; `IMPORT-MANIFEST.md` lists every file), the window, the Record screen and the editing screen are built. The cursor highlight and the installer are not. Only the Record screen has been run on Windows; the editing screen has been run in a browser with a pretend recorder, not on Windows.

## The first real recording (2026-10-23)

Made by the owner with the app on a Windows computer with 32 processor cores, from the recorder's own report, which the owner sent. Kept in a folder the owner chose on the Desktop.

- 13.6 seconds, 409 pictures. Windows read the saved video back as 13.6 seconds, and the sound track of the video as 13.6 seconds, the same as the recording time.
- The microphone (a webcam's microphone) was recorded: 13.6 seconds, loudest moment good (peak 0.22). Its sound card ran 31 ms fast against the computer's clock over the recording, and the program corrected for it; at worst the sound was 31 ms behind its picture.
- The computer's own sound was recorded as 13.6 seconds of silence, and the recorder said so as a problem: nothing was heard from the speakers. That is what happens when nothing is playing. It was not tried with something playing.
- The keys that work from any program (Ctrl+Shift+F10, F11 and F12) were registered.
- The program used about 46 percent of one core, which the recorder projected as 11.5 percent of a 4-core laptop, against a target of 10 percent. That needs a real measurement on a modest laptop.

Not yet tried in the app: one window, part of a screen, the webcam, a long recording, the keys with another program in front, and any screen reader.

### Two faults found while building it, both also in OpenStage Author

Found by reading the code before checking the screens, and then caught by a browser check written for each.

1. **A new edit of the newest recording could never be saved when an edit had been saved before.** The screen first copies the older edit to `edit-before-take-N.json`, but the folder only allowed `edit.json` to be written, so the copy was refused, and with it the save. Nothing was lost (it refuses), but the new edit stayed unsaved. Here the shell has a second command that writes only that file, never over an existing one (`recording_keep_edit`), with tests in Rust and in the browser.
2. **"Make a video" on a recording that had never been edited and saved was refused by the video maker** ("There is no edit to export"), because the screen saved only when something had changed. Here the edit is saved first whenever the saved file is not the edit on the screen. The pretend recorder now refuses the same way the real video maker does, so a browser check would catch it coming back.

Both faults are in OpenStage Author's `editor/src/editrecording.ts` and `recordingfolder.ts` as copied (main, commit `01fc056`). I have not changed that repository and will not without the owner's yes.

## Hiding windows, and picking a window by clicking it (2026-11-01)

The two remaining "finish the recorder" items from the first list that needed the Windows part of the engine. Both are in the shared engine, so they are in OpenStage Author's copy too.

**Hide windows** (requirement A7: "I can choose windows to exclude. Excluded windows appear blank or blurred in the recording"). On the Record screen, **Hide windows with these words in their title or program name**, words separated by semicolons, kept for next time. Windows' screen capture takes the whole screen and cannot leave out another program's window, so the recorder covers the windows in every picture before it is encoded: wherever such a window is on the screen, the video has a plain dark grey box and nothing of the window is kept. `record --hide <word>` (given once for each word, at most 8) is the option underneath, and it says in words what it will do before the countdown. Choices of mine, each reversible:
- A plain box, not a blur (a blur of a password manager can still be read at low strength, and a box cannot).
- The whole box of the window is covered, even where another window is in front of it. That hides a little more than it has to and never less.
- A window that opens is covered within a tenth of a second, so a pop-up can show for a few pictures; a window that is moved or resized is followed at once.
- It is for a screen or part of a screen. A recording of one window shows nothing but that window, so `--hide` with `--window` is refused, and the Record screen says so.
- The notes of the mouse (`--interactions`) still name the window in front, hidden or not. The webcam and the sound are not changed. Nothing is hidden from anyone watching the screen while recording. The Record screen says all of this beside the box.
- Quick record follows the same box and says so.
- **Checked on real Windows** with windows the test made itself, and nothing else on the screen looked at: a test creates real windows and checks they are found by their title (capital letters do not matter), followed when moved without waiting, found within a tenth of a second when they open, left alone when hidden or minimized, and never the recorder's own. Then two real 2-second recordings of a small part of the screen holding only one of those windows: without `--hide`, 86 percent of the pictures' pixels were that window's colour, and with `--hide "secret test"`, 99.3 percent were the dark grey cover, the rest being the edge of the window's shadow. Plus 13 tests with a pretend screen.

**Pick a window by clicking it.** On the Record screen, with One window chosen, **Pick a window by clicking it** puts this app's window on the taskbar, waits for a click (`openstage-capture pick-window`), brings the app back, and selects the window that was clicked. The click only chooses: both the button going down and coming up are kept from the window under the mouse, so nothing in it is pressed. Escape cancels; it gives up after 30 seconds. A click on the desktop, the taskbar or a window with no title says so. The list of windows and typing part of a title still work, and are the way without a mouse.
- **Checked:** 5 tests of the wording with a pretend screen, 3 browser checks, and on real Windows a test that makes a window, clicks it (the mouse jumps there for a moment) and finds it. That test did not click when another window was on top of the test window's middle, so it said so and stopped, and I cannot say it ran its click; the hooks were seen to catch and name a real click on another program's window once (the author's own click while a test ran, which it swallowed). **Not checked:** that a click really is kept from the window under it, and how it feels with a real mouse and a screen reader.

**The 1.3 second pause after the countdown** was already fixed before this product existed (the start-up is done during the countdown; `docs/capture/roadmap.md` has the measurement: 0.08 to 0.16 seconds with a countdown). I saw the same thing in a real recording today: with a countdown of 0, the video file was ready 1.16 seconds after the start. With a countdown of 0 there is nothing to do it during, and the video starts about 1.2 seconds after the start; the Record screen's countdown is 3 seconds by default.

## Noting the mouse, and zooms suggested from the clicks (2026-11-01)

**A gap, found while building the next thing.** The Record screen could never turn on noting the mouse: its code said the choice was "never switched on from here", written before the pointer ring existed. So nothing recorded in this app could show the pointer ring or give zooms from clicks. It is now a box on the Record screen, **Note where the mouse goes and where I click**, off to start with, kept for next time, which asks the recorder for `--interactions no-keys`. The keys that are pressed are never noted from here, and the words beside the box say that the notes also say which window was in front and the name of what was clicked, which can give away private things. Quick record uses the same choice and says so in its sentence.

**Suggested zooms** (the requirement "Capture can suggest zooms from where I clicked. I accept, edit, or reject each one"). A button on the editing screen, **Suggest zooms from my clicks**, lists zooms made from the noted clicks. Each can be added, left out, or all added at once; nothing is added by itself. The rules are in `capture-edit/src/suggest.ts` and are plain enough to say in words:
- Clicks no more than 4 seconds apart, and not spread over more than about half the picture, are one moment.
- A zoom starts 1 second before the first click of a moment and ends 1.5 seconds after the last, between 2.5 and 12 seconds long, showing between a third and two thirds of the picture's width (1.5 to 3 times closer), centred on the clicks and kept inside the picture.
- No suggestion overlaps another or a zoom already in the edit; at most 10, the busiest moments first. Only the part of a take that the edit uses counts.
- **The description of a suggested zoom is left empty on purpose.** A suggestion knows where you clicked, not what the picture shows, and a guess would let a zoom with no real description pass as finished. The edit asks for one, as it does for any zoom. What was clicked (the name Windows gave the item) is shown in the list only when every click of the moment was on the same named thing.
- For a part of a screen the take says where the part starts and how big it is. For a whole screen the picture is the display, whose size the take does not say, so the app reads it from the video; when it cannot, it says so in words and suggests nothing.
- **Not built:** the same button in OpenStage Author's own recording editor (the rules are shared, so it is a small step), suggested steps or step text, settings for the numbers above (they are constants at the top of `suggest.ts`).
- **Checked:** 12 tests of the rules, 5 of reading a recording for them, one of the session adding a zoom at its own time, and 6 browser checks. **Never tried on a real recording** (the clicks come from the pretend recorder), and nobody has looked at whether the suggested zooms land where a person would want them.

## Quick record (2026-11-01)

Built from the list item "tray start, countdown, save, copy the path": the part of a quick-capture tool that needs no server. The choices below are mine and each can be reversed.

- **No new settings.** Quick record uses the Record screen's choices as they stand (the screen, the voice, the computer's sound, the webcam, the countdown and the sounds for each step), with a name made from the time, such as `Quick recording 2026-11-01 1405`. A sentence under the button says exactly what it will do and how to stop it, worked out from the same choices, so nothing is recorded that the screen did not say.
- **A window is not remembered from one run to the next**, so a quick recording of "one window" records the whole screen, and the sentence says so. A part of a screen is kept.
- **Stopping makes the video.** When the recording is stopped (the Stop button, Ctrl+Shift+F11 from any program, or Stop recording in the icon's menu), the app makes an edit from the takes with no cuts, saves it, makes `exports/<name>.mp4` with the same video maker as Make a video, and puts the video's path on the clipboard. The Record screen then shows the path in a box (it can be selected), **Copy the path**, **Show the video in its folder**, and the usual **Edit the recording I just made**. If the clipboard cannot be used, it says so and Copy the path tries again. It is an ordinary recording, so it can be edited afterwards. The words about the missing captions are still said.
- **The icon in the notification area** (the "tray"), with Quick record, Stop recording, Show OpenStage Recorder and Quit. A click on the icon shows the window. Quick record from the icon puts the window on the taskbar so it is not filmed, and brings it back when the recording ends, to show the video and its path. Its tooltip says what is happening ("recording. Stop with Ctrl+Shift+F11", "making the video", "your quick recording is ready"). Quit is the window closing, so a recording still going is asked about in the same way.
- **Not built:** a key that starts a recording from any program (the keys work only while a recording goes on); a separate profile for quick recordings; starting with the window closed (the app has to be open, and can be on the taskbar); closing the window to the icon (closing still quits).
- **The clipboard** is written by the shell through the official Tauri clipboard plugin, called from Rust, so the page gets no new permission. The icon needs Tauri's `tray-icon` feature. Together they add 18 libraries (277 in all); the licence check passes.
- **Checked:** the plain rules and the whole run with the pretend recorder (11 tests), the Rust rules for the icon's tooltip and the clipboard text (5 tests), 7 browser checks, and the shell compiles. **Never tried on Windows**: the icon, putting the window away, the clipboard, and a recording started this way.

What changed is where things sit and how they look.

## What it is

A light screen recorder for Windows that works on its own, away from OpenStage Author. You pick what to record: an app (one window), a screen, or part of a screen. It records your microphone and the computer's sound, and the webcam if you choose. A simple editor lets you cut it up, add transitions, blur part of the picture, zoom in, and highlight the cursor. It saves an MP4. Captions are made outside the program to start with.

It has no courses, slides, quizzes or publishing. **OpenScreen** stays the name of the recorder inside OpenStage Author. **OpenStage Recorder** is the standalone product.

## What already exists in the recording engine

From OpenStage's code as it stands today (main, commit 01fc056). Checked by reading, not by running.

- Recording a whole screen, one window, or a region (typed numbers, or dragging a rectangle with a keyboard version).
- Microphone, the computer's sound, pause and resume, hotkeys that work in other programs, spoken cues, saving that survives a crash, and a check of the recording afterwards.
- The webcam, recorded as its own file beside the screen, with a list of cameras. At export it can be drawn as a small picture in picture. Its recorder checks passed on a Windows work PC on 2026-10-15; how the picture looks, and whether it lines up with the voice, were not confirmed when it was handed over, and I have not seen a later result.
- Editing: split, trim, delete, join, move, volume and fades, transitions (fade, cross-fade, wipes, slide), blur and zoom (including a zoom drawn from a rectangle), undo and redo, a preview that plays, and export to MP4. Blur and zoom are drawn by the exporter itself, so they add no new library or download.
- The pointer can be included in the picture as it is (a Windows setting).

## What is new work

1. **The app itself**: a small window with the recorder and the editor, its keyboard paths, its settings, file dialogs, an icon, a double-click build script and an installer.
2. **A simple editor screen**: the existing editing screens, with the tools you did not ask for (text overlays, shapes, arrows, redaction) left out of view. Blur and zoom stay, and so does the webcam. Each needs a way to place a rectangle on the picture with the keyboard, in words as well as by dragging; the edit model already says where a rectangle is in words.
3. **The webcam controls**: choose a camera, turn it on or off before recording, see it in the preview, and choose where the small picture sits and how big it is.
4. **Cursor highlight**: not built anywhere yet. It is in the requirements (story C6) but the exporter does not draw it. There are two ways to do it:
   - *Drawn when exporting*, from the cursor positions the recorder can write down. You can switch it on or off after recording. This is more engine work, and it would record the pointer's position and clicks only, not window titles, clicked item names or keys. **My recommendation.**
   - *Drawn while recording*, by a small ring window that follows the pointer and gets recorded with the screen. Simpler, but it cannot be undone afterwards, and it would not appear when recording a single window.

## Assumptions you can veto

- No text overlays, shapes or arrows in the first version. The engine can do them, so they can come back later. Redaction (the Cover tool, a blackout) was left out at first and added on 2026-10-25 at the owner's request.
- Captions are made outside the program in the first version, as you said. The program neither makes nor edits them, and there is no speech model to download, which keeps it light. One suggestion, which you can decline: when an export finishes, the program says in plain words that the video has no captions, and that a `.vtt` file with the same name as the video, kept beside it, is how most players find captions. A program that makes video should not let the missing captions go unmentioned. Captions made inside the program can come later.
- The recording folder format stays the same as in OpenStage Author, so a recording made in one opens in the other.

## Where it lives

The owner chose to pull the parts this product needs out of OpenStage Author into a folder of its own, rather than share one tree. The recording engine here is therefore a copy, taken at a named OpenStage commit (01fc056), with a manifest.

The cost is drift. In the first week after OpenStage Author took in the recorder, 17 commits touched the recorder folders there. Only 3 touched the Rust recording program. The rest were in the edit model and the editing screens, which are the parts this product copies and trims. A fix made in one place has to be carried to the other by hand, and each carry is something the owner says yes to. To keep that cheap, the copied folders keep the same paths as in OpenStage Author and are changed only when the product needs it.

**Still open:** whether this folder becomes its own GitHub repository (`openstage-recorder`, which the owner would create empty) or sits inside the OpenStage Author repository. Nothing has been pushed anywhere.
